# Docs Repository Overview

This page explains how the Enact documentation repository is structured and how the documentation website is built.

## How Docusaurus Works

[Docusaurus](https://docusaurus.io/) is a static site generator optimized for documentation. It works by:

1. **Content as Markdown/MDX** — Documentation lives in the `docs/` folder as `.md` or `.mdx` files. MDX extends Markdown with JSX, allowing you to embed React components directly in documentation.

2. **Config-driven** — `docusaurus.config.js` defines the site title, theme, plugins, and navigation. The `sidebars.js` file controls the documentation sidebar (we use `autogenerated` to derive it from the folder structure).

3. **Build process** — Running `yarn start` or `yarn build` compiles MDX into static HTML, bundles JavaScript/CSS, and outputs the site to `build/`. Docusaurus handles routing, search, and code highlighting out of the box.

4. **Custom components** — React components in `src/components/` can be used in MDX. For example, the `LiveExample` component embeds iframe-based interactive examples in the docs.

## Folder Structure

| Folder | Purpose |
|--------|---------|
| **`docs/`** | All documentation content. Contains both **static docs** (manually written `.md` files from the Enact repos) and **generated docs** (`.mdx` from JSDoc via `jsonParser`). Subfolders like `core/`, `sandstone/`, `ui/`, `spotlight/` mirror the Enact module structure. |
| **`src/`** | Docusaurus source files: custom pages (`pages/`), components (`components/`), and styles (`css/`). The `src/pages/docs/modules/` tree holds **JSON** output from Documentation.js (input for `json-to-mdx`). |
| **`scripts/`** | Build and parsing scripts. See [Workflow](#documentation-workflow) below. |
| **`sample-runner/`** | Enact sample apps (core, sandstone, moonstone, limestone, agate). Built into `static/*-runner/` for live examples. |
| **`static/`** | Generated at build time. Contains built sample runners (`core-runner/`, `sandstone-runner/`, etc.) served as static assets for live examples. |
| **`raw/`** | (Generated, gitignored) Clones of `enact`, `cli`, and `eslint-config-enact` from GitHub. Created by `DocParser` when running `parse-docs`. |
| **`src/data/`** | (Generated, gitignored) Output from `DocParser`: `docIndex.json`, `libraryDescription.json`, etc. |

### Scripts

| Script | Role |
|--------|------|
| **`DocParser.js`** | Uses `@enact/docs-utils` to parse JSDoc from Enact packages, generates JSON into `src/pages/docs/modules/`, copies static docs into `docs/`, and produces `src/data/docIndex.json`. Imports `prepareRaw.js` to clone repos into `raw/` if needed. |
| **`jsonParser.js`** | Reads JSON from `src/pages/docs/modules/`, converts it to MDX in `docs/`, injects `LiveExample` for runnable code from JSDoc `@example` tags, and applies content fixes (escaping, GitHub URLs, etc.). Runs `fixAllStaticDocs()` on all docs after conversion. |
| **`make-runner.js`** | Builds sample runners from `sample-runner/*` into `static/*-runner/` using the Enact CLI. Required for live examples to work. |
| **`prepareRaw.js`** | Clones Enact-related repos into `raw/`. Invoked as a side effect of `DocParser`. |

## Documentation Workflow

### 1. Parse docs

```bash
npm run parse-docs
```

- Clones `enact`, `cli`, `eslint-config-enact` into `raw/` (if not present)
- Parses JSDoc and generates JSON into `src/pages/docs/modules/`
- Copies static documentation into `docs/developer-guide/`, `docs/developer-tools/`, etc.
- Writes `src/data/docIndex.json` and `libraryDescription.json`

### 2. Convert JSON to MDX

```bash
npm run json-to-mdx
```

- Reads all `*.json` files under `src/pages/docs/modules/`
- Generates `.mdx` files in `docs/` (core, ui, sandstone, spotlight, i18n, webos)
- Injects `LiveExample` components for JSDoc `@example` snippets with runnable code
- Fixes MDX issues in all docs (backslashes, angle brackets, `{expression}` escaping)
- **This step is specific to Docusaurus** — see [Comparison with Gatsby](#comparison-with-gatsby) below

### 3. Build sample runners (optional, for live examples)

```bash
npm run make-runner
```

- Builds `sample-runner/core`, `sample-runner/sandstone`, etc. into `static/core-runner/`, `static/sandstone-runner/`, etc.
- Live examples load these built apps in iframes

### 4. Run or build the site

```bash
yarn start      # Development server (hot reload)
yarn build      # Production build into build/
```

## Comparison with Gatsby

The previous docs site used **Gatsby**, which consumed JSON from Documentation.js directly via plugins. The Docusaurus flow adds an explicit **JSON → MDX** conversion step.

| Aspect | Gatsby | Docusaurus |
|--------|--------|------------|
| **Doc source** | JSON from Documentation.js | MDX (Markdown + JSX) |
| **Consumption** | Gatsby plugins read JSON at build time | Docusaurus reads `.mdx` files from `docs/` |
| **Extra step** | None — JSON was the source of truth | **`json-to-mdx`** — we must convert JSON to MDX before Docusaurus can render it |
| **Static docs** | Copied and rendered similarly | Same: DocParser copies static files; `fixAllStaticDocs` post-processes them |
| **Live examples** | Similar iframe-based approach | Same: `LiveExample` + built runners in `static/` |

**Why the extra step?** Docusaurus is file-based: it expects markdown files in `docs/`. Documentation.js outputs JSON, so we use `jsonParser.js` to transform that JSON into MDX. Gatsby, by contrast, could plug directly into a data layer (GraphQL) and render JSON-driven pages without an intermediate file format.

**Summary:** The `json-to-mdx` step is the main difference. Run it whenever you update the parsed JSON (e.g. after `parse-docs` or after changing `jsonParser` logic).
