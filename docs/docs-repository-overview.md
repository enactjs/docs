# Docs Repository Overview

This page explains how the Enact documentation repository is structured and how the documentation website is built.

## How Docusaurus Works

[Docusaurus](https://docusaurus.io/) is a static site generator optimized for documentation. It works by:

1. **Content as Markdown/MDX** — Documentation lives in the `docs/` folder as `.md` or `.mdx` files. MDX extends Markdown with JSX, allowing you to embed React components directly in documentation.

2. **Config-driven** — `docusaurus.config.js` defines the site title, theme, plugins, and navigation. The `sidebars.js` file controls the documentation sidebar (we use `autogenerated` to derive it from the folder structure).

3. **Build process** — Running `npm start` or `npm run build` compiles MDX into static HTML, bundles JavaScript/CSS, and outputs the site to `build/`. Docusaurus handles routing, search, and code highlighting out of the box.

4. **Custom components** — React components in `src/components/` can be used in MDX. For example, the `LiveExample` component embeds iframe-based interactive examples in the docs.

## Folder Structure

| Folder | Purpose |
|--------|---------|
| **`docs/`** | All documentation content. Contains both **static docs** (manually written `.md` files from the Enact repos) and **generated docs** (`.mdx` from JSDoc via `jsonParser`). Subfolders like `core/`, `sandstone/`, `ui/`, `spotlight/` mirror the Enact module structure. |
| **`src/`** | Docusaurus source files: custom pages (`pages/`), components (`components/`), and styles (`css/`). The `src/pages/docs/modules/` tree holds **JSON** output from Documentation.js (input for `json-to-mdx`). |
| **`scripts/`** | Build and parsing scripts. See [Workflow](#documentation-workflow) below. |
| **`sample-runner/`** | Enact sample apps (core, sandstone, moonstone, limestone, agate). Built into `static/*-runner/` for live examples. |
| **`static/`** | Generated at build time. Contains built sample runners (`core-runner/`, `sandstone-runner/`, etc.) served as static assets for live examples. |
| **`raw/`** | (Generated, gitignored) Clones of `enact`, `cli`, and `eslint-config-enact` from GitHub. Created by `DocParser` when running `parse-docs`. |
| **`src/data/`** | (Generated, gitignored) Output from `DocParser`: `docIndex.json`, `libraryDescription.json`, etc. |

### Scripts

| Script | Role |
|--------|------|
| **`DocParser.js`** | Uses `@enact/docs-utils` to parse JSDoc from Enact packages, generates JSON into `src/pages/docs/modules/`, copies static docs into `docs/`, and produces `src/data/docIndex.json`. Imports `prepareRaw.js` to clone repos into `raw/` if needed. |
| **`jsonParser.js`** | Reads JSON from `src/pages/docs/modules/`, converts it to MDX in `docs/`, injects `LiveExample` for runnable code from JSDoc `@example` tags, and applies content fixes (escaping, GitHub URLs, etc.). Runs `fixAllStaticDocs()` on all docs after conversion. |
| **`make-runner.js`** | Builds sample runners from `sample-runner/*` into `static/*-runner/` using the Enact CLI. Required for live examples to work. |
| **`prepareRaw.js`** | Clones Enact-related repos into `raw/`. Invoked as a side effect of `DocParser`. |

## Documentation Workflow

### 1. Parse docs

```bash
npm run parse-docs
```

- Clones `enact`, `cli`, `eslint-config-enact` into `raw/` (if not present)
- Parses JSDoc and generates JSON into `src/pages/docs/modules/`
- Copies static documentation into `docs/` (e.g. developer-guide, developer-tools)
- Writes `src/data/docIndex.json` and `libraryDescription.json`

**Useful options** (pass after `--`): `--extra-repos owner/repo#branch,...` (e.g. `enactjs/agate#develop`), `--rebuild-raw` (re-clone all repos), `--enact-branch <branch>`. See `scripts/DocParser.js` and `scripts/prepareRaw.js` for the full list.

### 2. Convert JSON to MDX

```bash
npm run json-to-mdx
```

- Reads all `*.json` files under `src/pages/docs/modules/`
- Generates `.mdx` files in `docs/` (core, ui, sandstone, spotlight, i18n, webos)
- Injects `LiveExample` components for JSDoc `@example` snippets with runnable code
- Fixes MDX issues in all docs (backslashes, angle brackets, `{expression}` escaping)

### 3. Build sample runners (optional, for live examples)

```bash
npm run make-runner
```

- Builds themes (core, moonstone, sandstone, limestone, agate) from `sample-runner/*` into `static/*-runner/` using the Enact CLI
- Live examples load these built apps in iframes

**Options:** `--fast` (skip themes that already have a runner), `--enact-cmd=<cmd>` (e.g. `npx enact`).

### 4. Run or build the site

```bash
npm start           # Development server (hot reload)
npm run build       # Production build into build/
```

## Why JSON → MDX?

Docusaurus is file-based: it expects Markdown/MDX files in `docs/`. Documentation.js (used by `parse-docs`) outputs JSON. So we run **`json-to-mdx`** to turn that JSON into `.mdx` in `docs/`. Run it after `parse-docs` or after changing `jsonParser.js`.

---

## The `jsonParser.js` script

`scripts/jsonParser.js` is the **JSON → MDX** converter. It is run by `npm run json-to-mdx` and does the following.

**Input:** One or more `.json` files under `src/pages/docs/modules/` (Documentation.js output: JSDoc parsed into a tree of modules, classes, functions, props, etc.).

**Output:** One `.mdx` file per JSON file in `docs/`, with the same folder structure (e.g. `src/pages/docs/modules/ui/Button/index.json` → `docs/ui/Button/index.mdx`).

**Main flow:**

1. **Entry** — Collects all `.json` files under `src/pages/docs/modules/`, then for each file calls `main()`: read JSON → `generateMDX()` → escape for MDX → write `.mdx`.
2. **After all conversions** — Runs `fixAllStaticDocs()` over every `.md`/`.mdx` in `docs/` to fix backslashes in URLs, `&lt;--`, `{...}` in prose, etc.

**What `generateMDX()` does:**

- Builds **front matter** (title, description, sidebar_label) and **imports** (Tabs, TabItem, and LiveExample if the module has runnable examples).
- Outputs **module title**, **description** (from JSDoc), and **Exports** list if present.
- **API Reference** — Groups static members by `kind` (functions, classes, constants, typedefs, other). For each:
  - **Functions / Classes / Constants / Type definitions** — Each member is rendered by `generateMemberMDX()`: heading with type badge (e.g. Component, HOC), description, **usage block** (import statement), **Extends** / **Includes** (from JSDoc tags), then for classes: a single **Properties** section (instance members including callbacks like `onScrollStart`), optional **Constructor** (signature and params from `constructorComment`, e.g. `Job(fn, timeout)`), **Methods** (members tagged `@method`), **Configuration** for HOCs (from `defaultConfig`), then static members. For functions, object-style params get an **Object keys for options** subsection. Constants and typedefs with `properties` use a **Properties** list (no Tabs). For typedefs, a list of shape properties.
  - **Types** — Rendered as strings (e.g. union of string literals → `'above', 'after'`; quoted literals use a “literal” style). Type pills in the UI use classes like `api-type`, `api-type-string`, `api-type-literal` (see `docs-theme.css`).
- Appends a **Variable Types Key** (Array, Boolean, Function, …) at the end of the API Reference.

**Helpers worth knowing:**

- **`mdastToMarkdown()`** — Converts the Markdown AST (MDAST) from Documentation.js (paragraphs, links, code blocks, lists) into a markdown string; JSDoc links like `ui/VirtualList.VirtualGridList` are turned into site links via `mixNameToDocLink()`.
- **`escapeMdxExpressions()`** / **`escapeDescriptionPreservingCodeBlocks()`** — Escape `{` and `}` (and similar) so MDX does not treat them as JSX expressions; code blocks are preserved so syntax highlighting still works.
- **`generateUsageBlock()`** — Produces the import snippet (e.g. `import Button from '@enact/ui/Button'`) as fenced markdown so Prism can highlight it.
- **`generateExamplesSection()`** — For `@example` tags: if the example is runnable, outputs a `<LiveExample>` component; otherwise outputs static code blocks. Runners are chosen via `getRunnerFromModule()` (e.g. theme from module path).

**Static docs:** After writing all MDX, `fixAllStaticDocs()` walks `docs/` and applies `fixStaticDocsContent()` to every `.md` and `.mdx` (fix GitHub URLs, `&lt;--`, `&lt;email&gt;`, and `{...}` escaping). Authored root docs such as `docs/api.mdx` (which contain JSX like `{card.to}`) are **not** run through `escapeMdxExpressions()`, so their expressions are left intact and the page compiles correctly.

## Recent work (last 9 commits)

In the most recent work, the focus was on bringing the generated API output and the Docusaurus site behavior closer to the reference Enact documentation.

- **Edit on GitHub behavior**: started refactoring how edit links are produced so that API pages can link back to the correct source repository instead of always pointing to this docs repo.
- **Required markers in API**: iterated on the rules for when properties show a visible “Required” indicator, so it matches the reference site more closely and avoids incorrectly marking props as required.
- **Navigation correctness**: fixed navbar active-state behavior (notably “Home”) so it only highlights on the exact `/` route.
- **Generated docs hygiene & stability**: reduced friction from generated static docs (developer-guide / developer-tools) and MDX-compat issues by keeping the generated content under control and aligning the workflow/docs accordingly.
- **Site content & assets**: updated pages, styling, and supporting assets (icons/images) to match the target look-and-feel.
- **API overview**: added/iterated on the API overview page and supporting data so the “libraries” presentation matches the reference docs direction.
